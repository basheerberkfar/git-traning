# Exercise 4 — Request Lifecycle: From URL to JSON

Imagine entering `https://jsonplaceholder.typicode.com/posts/1` in a browser or sending the URL via `fetch()` or curl. The client needs to locate the server, establish a secure connection, send an HTTP request, wait for the server to handle it, and finally interpret the HTTP response.

First, the client parses the URL. The `https` scheme says that the application should use HTTP over a secure TLS connection. The hostname is `jsonplaceholder.typicode.com`, and `/posts/1` is the resource path; if a query string such as `?userId=1` were present, it would supply additional request parameters. A browser may also consult cache, DNS cache or an existing connection before opening a new connection.

Next comes **DNS** (Domain Name System). Humans use names, but network packets need addresses. The computer typically asks a DNS resolver for the address or addresses associated with the hostname. DNS answers may already be cached, and some deployments point first to a CDN or proxy rather than directly to the application server. The client then uses the returned address to reach the destination.

For **HTTPS**, the client and remote endpoint negotiate a protected connection. At a high level, TLS helps authenticate the server using a digital certificate and encrypts traffic between the client and the TLS endpoint. HTTPS protects the request URL path, headers and response body while in transit on that connection (though not necessarily all connection metadata). Modern HTTP can run over different transports, so the exact low-level connection steps vary by HTTP version. The important idea is that the application exchanges HTTP messages over a secured channel.

The client creates an **HTTP request**, for example `GET /posts/1`, supplying an authority/host, the path and request headers. A GET request generally asks the server to return data rather than change it. The client can also send headers such as `Accept: application/json`; methods like POST commonly include a request body and `Content-Type` declaring that body's format.

The request travels across the network, often through DNS-selected edge infrastructure, load balancers or a reverse proxy. The **server** (or an API handler behind these intermediaries) routes the request to the correct handler. It may validate the path and parameters, check permissions, read from memory or a database, run application logic and serialize its result as JSON. On a mock API, the backend may return predefined test data instead of consulting a normal production database.

The server creates an **HTTP response** with a status code, response headers and usually a body. For example, `200 OK` signals that retrieval succeeded and `Content-Type: application/json` describes a JSON response. A `404 Not Found` may mean the requested resource does not exist, whereas `400 Bad Request` often means the request is invalid. A `500` status generally indicates an unexpected server-side problem. The status says what broadly happened; the body supplies the returned resource or error details.

The response travels back along the established connection. TLS protects the data in transit, and the client decrypts it before the application reads it. A browser or frontend library makes the response accessible to JavaScript. With `fetch`, the code can check `response.ok` or `response.status`, and `await response.json()` parses a valid JSON response body into JavaScript data. Importantly, `fetch` does not automatically reject its Promise just because the server returns 404; the application must inspect the status and decide how to handle it. If the response is not actually valid JSON, JSON parsing can fail.

Finally, the application can display a title, update the UI, log the result or show an error. Some responses may be cached and reused according to HTTP rules. In one request, DNS, network latency, TLS negotiation, server processing, database reads and response size all contribute to overall performance. Reading response status and headers alongside the body is therefore essential when debugging API issues.
